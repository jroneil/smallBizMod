# ADR-DOC-002: Storage abstraction (FR-11) and reference implementation

- Status: Accepted (documentation/architecture decision; implementation not yet authorized)
- Date: 2026-08-27

## Context

Framework FR-11 requires that "the framework SHOULD provide an abstraction for
document/object storage so customer deployments can select an approved
implementation without business modules depending directly on a specific cloud
vendor." The merged Technical Architecture v0.1 deliberately left the shape of
that abstraction open ("object-storage abstraction details", Section 22) and
listed "storage abstraction" among the evidence-triggered later ADRs, with the
explicit note that it is not needed "until Document or another selected
capability demonstrates the need" (Codex proposal; the DeepSeek proposal
recorded the same deferral). Document is now selected, so this is the moment
the FR-11 decision was deferred to.

The reference deployment is one application process and one PostgreSQL
database (NFR-05, ADR-003), with no object-storage service in the Compose
environment. NFR-07 forbids new infrastructure without a demonstrated
requirement, and the PRD technology baseline says the concrete storage is
"selected per deployment". The abstraction itself is required by FR-11
(SHOULD); the concrete implementation for the reference deployment is a
deployment decision.

## Decision

### Framework contract

- `sbp-framework` gains a minimal, provider-neutral storage contract under
  `com.oneilsoftware.sbp.framework.storage`:

  ```text
  BlobStorage
      void store(String key, byte[] content, String contentType)
      Optional<byte[]> load(String key)
      void delete(String key)
  ```

- The contract carries no Spring or business-module dependencies, mirroring the
  audit-hook contract pattern (ADR-UM-003): the framework artifact remains a
  plain JAR.
- The contract is deliberately minimal: store/load/delete by opaque key. No
  multipart orchestration, streaming protocol, retention, or vendor-specific
  capability is in the contract. Content larger than the module's configured
  upload limit is rejected before it reaches storage, so `byte[]` is an honest
  and simple payload for the baseline.

### Reference implementation

- The Document module ships a **database-backed** `BlobStorage`
  implementation as its default: content is stored as `bytea` in the
  module-owned `sbp_document_content` table (storage_key UUID primary key,
  content, stored_at), reached only through the `BlobStorage` contract.
- The default is registered in the module auto-configuration guarded by
  `@ConditionalOnMissingBean(BlobStorage.class)`, so a customer deployment can
  supply its own approved implementation (for example S3, MinIO, or a
  filesystem store) by defining one `BlobStorage` bean — no Document module
  change is required.
- The storage key is the Document's UUID, generated by the module and never
  exposed as a contract.

### Why database-backed for the reference, and what was rejected

- **PostgreSQL `bytea` (chosen):** zero new infrastructure (NFR-07); preserves
  the one-database-per-customer model (NFR-05); database backups and restore
  cover document content (NFR-06); metadata and content can be written in one
  transaction by the reference implementation; adequate for small-business
  volumes (thousands of documents, bounded file sizes).
- **Filesystem store:** rejected for the reference because it introduces
  container-volume lifecycle and backup asymmetry with the database without a
  demonstrated benefit; it remains a valid customer-selected implementation of
  the same contract.
- **MinIO / S3-compatible service in the reference Compose environment:**
  rejected because it adds a new service for no demonstrated v0.1 need
  (NFR-07). It is the expected customer-selected implementation for a
  deployment that already has object storage; those customers supply their own
  approved `BlobStorage` implementation.

### Transaction and failure semantics

- The contract is synchronous and does not promise atomicity across stores.
  The database-backed implementation participates in the module's transaction,
  so metadata and content are stored atomically in the reference.
- The Document application service treats content storage as the first step of
  a create/replace and performs best-effort cleanup (`delete`) if the metadata
  transaction subsequently fails. A remote-store implementation supplies its
  own failure semantics under its deployment's policy; this is documented
  behavior, not an abstraction promise.

## Consequences

- FR-11 is realized with the smallest contract that proves the property that
  matters: the Document module contains no storage-vendor code and no
  assumption about where bytes live.
- The reference deployment gains no service and no volume; content lives inside
  the existing PostgreSQL database and is covered by its backup/restore.
- A customer moving to object storage replaces one bean, not module code or the
  module contract; the migration path is the deployment's responsibility.
- The framework artifact grows one small contract with no new dependencies,
  consistent with its role as the home of cross-cutting contracts.
- `byte[]` payloads bound content to the module's size limit; deployments
  needing streaming of very large files must revisit the contract with real
  evidence (P-02, NFR-07).
